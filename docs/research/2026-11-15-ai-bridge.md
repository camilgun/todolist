# Research: the AI bridge

> Date: 2026-11-15 · GitHub issue #2, "Research: the AI bridge" · Context: [IDEA.md](../../IDEA.md), [ADR 0001](../adr/0001-native-mac-app-swiftui.md), [ADR 0002](../adr/0002-data-in-sqlite.md)
> Decision already taken (ADR 0002): from iteration 2 the AI reads and changes the data only through tools the app exposes and validates, never by writing to the database. This note researches how to build that bridge.
> Primary sources only, each opened on 2026-11-15; versions and dates are the ones observed that day. What I could not verify is marked **[not verified]**. Nothing here was tried in a prototype: every "works" below means "documented", not "tested".

## 1. Outcome in brief

I recommend that **all the rules live in one Swift library** (the "core": the tables, the migrations, and one function per operation such as "add task" or "split task into steps"), and that the AI bridge be **a small second executable in the same Swift package** that links that library and speaks MCP (Model Context Protocol, the protocol through which AI tools call external tools) over **stdio** (the AI tool starts the executable itself and talks to it through standard input and output). The app and the bridge are then two processes using the same code on the same SQLite file, which SQLite supports in WAL mode (write-ahead logging: readers and one writer at a time can work concurrently on the same machine). Nothing about validation is written twice, the bridge works even when the app is closed, and no network port is opened.

The price is the official Swift MCP SDK (software development kit): it is still classified as experimental (tier 3), its last release (0.12.1, May 2026) implements the previous protocol revision (2025-11-25), not the current one (2026-07-28), and it only works today because clients such as Claude Code still fall back to the old handshake. To contain that risk, the MCP part must stay a thin adapter of a few dozen lines per tool, with no rules in it.

**Runner-up:** the same Swift core exposed as a **command-line tool** with JSON output, and a **TypeScript** stdio MCP server (tier 1 SDK, current protocol) that only translates each tool call into one invocation of that command. Validation is still in one place; the cost is a second language, a Node.js dependency and one process launch per call.

**What would change the choice:**

- If the Swift SDK does not connect reliably to the AI tools actually used (to be tried first thing in iteration 2), or clients stop accepting the old handshake before the SDK supports the new one → the runner-up.
- If the only AI tool is a terminal coding agent (which can run commands), the command-line tool plus an agent skill is enough and cheaper in tokens than MCP; MCP is needed for AI tools that cannot run commands, such as a desktop chat app.
- If the app is ever distributed through the Mac App Store (sandbox mandatory) → the database must move to an app group container and the bridge needs a different packaging (section 2.3).
- If the user interface must update the instant the AI changes something, and a cross-process notification proves insufficient → an MCP server inside the app process over HTTP, accepting that it only works while the app runs.

## 2. Where the MCP server lives and which transport

### 2.1 The two standard transports

The current specification (2026-07-28) defines two standard transports ([Transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)):

- **stdio.** "The client launches the MCP server as a subprocess"; messages are JSON-RPC, one per line, on standard input and output; the server must write nothing else to standard output and may log to standard error. The client ends the server by closing its input, and should restart it if it exits unexpectedly ([stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)).
- **Streamable HTTP.** Every message is an HTTP POST to a single endpoint of a server that is already running. For local use the specification requires the server to validate the `Origin` header (to prevent DNS rebinding, an attack where a web page reaches a local server), and recommends binding only to `127.0.0.1` and authenticating connections ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)).

Custom transports are allowed; over a Unix domain socket or TCP the specification recommends reusing the stdio framing ([Transports, custom](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports#custom-transports)). No AI tool I looked at documents connecting to a local server over a Unix socket, so this is useful only between our own processes.

Since revision 2026-07-28 the protocol is stateless: the `initialize` handshake and sessions were removed, and every request carries its protocol version ([Key changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). This matters for the SDK choice (section 3).

### 2.2 The three places, compared

| | Inside the app process | Helper executable (recommended) | Separate program in another language |
|---|---|---|---|
| Transport | Streamable HTTP on `127.0.0.1` (stdio is impossible: the client would have to launch the app itself as its subprocess) | stdio | stdio |
| Works when the app is closed | ❌ the AI tool gets a connection error; the app must be opened first | ✅ the AI tool starts it | ✅ |
| Rules written once | ✅ same process | ✅ same Swift library | ⚠️ only if it calls the Swift core (command line); otherwise duplicated |
| Who writes to SQLite | One process | Two or more processes (one per AI tool session, plus the app) | Same as helper |
| App sees AI changes | ✅ immediately | ⚠️ needs a cross-process signal or a reload (section 4.3) | ⚠️ same |
| Exposure | A listening port: `Origin` validation and authentication are on us | None beyond the user's own files | None |
| Setup in the AI tool | A URL | A command path | A command, plus a runtime (Node.js) |

**How AI tools start local servers.** Claude Code registers a stdio server with `claude mcp add --transport stdio <name> -- <command>`, or a project-level `.mcp.json`; it also accepts HTTP servers by URL ([Claude Code, MCP](https://code.claude.com/docs/en/mcp)). Claude Desktop reads `~/Library/Application Support/Claude/claude_desktop_config.json`, where each server is a command to launch ([Connect to local MCP servers](https://modelcontextprotocol.io/docs/develop/connect-local-servers)), and the Desktop app's local Code sessions load the same servers ([Claude Code, Desktop](https://code.claude.com/docs/en/desktop)). A server can also be packaged as an MCP bundle (`.mcpb`), which supports Node.js, Python and plain binary servers ([mcpb README](https://github.com/modelcontextprotocol/mcpb); last release v2.1.2, December 2025). Whether Claude Desktop's chat can be pointed at a plain `http://127.0.0.1` server without a bundle or a bridge is **[not verified]**.

**A detail to respect in a stdio helper.** Claude Code stops a stdio server with `SIGINT`, then `SIGTERM` 100 ms later, then `SIGKILL` after a further 400 ms ([Claude Code, MCP](https://code.claude.com/docs/en/mcp#how-claude-code-stops-a-stdio-server)). Because every operation is one short SQLite transaction, being killed mid-call loses at most that call; SQLite rolls an incomplete transaction back.

### 2.3 What the sandbox changes

The App Sandbox is mandatory only for the Mac App Store ([App Sandbox](https://developer.apple.com/documentation/security/app-sandbox)). ADR 0001 plans building from source, so iteration 2 can assume an **unsandboxed** app with its database in `~/Library/Application Support/…`, readable by a helper launched by any AI tool running as the same user. That is the simple case and the one recommended.

If the app were sandboxed:

- Its data would live in its own container under `~/Library/Containers`. From macOS 14, a process that is not sandboxed (such as a helper launched by an AI tool) and tries to read another app's container makes the system ask the user for permission ([Accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)).
- The documented shared location is an **app group container** (`~/Library/Group Containers/<team identifier>.<group name>`), which also permits Unix domain sockets between group members ([App Groups entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups), [`containerURL(forSecurityApplicationGroupIdentifier:)`](https://developer.apple.com/documentation/foundation/filemanager/containerurl(forsecurityapplicationgroupidentifier:))). This requires a signing team, hence the paid developer program.
- Apple's recipe for a helper tool embedded in a sandboxed app gives the tool exactly two entitlements, `app-sandbox` and `inherit`, meaning it inherits the sandbox of the app that launches it ([Embedding a helper tool in a sandboxed app](https://developer.apple.com/documentation/xcode/embedding-a-helper-tool-in-a-sandboxed-app), [Enabling App Sandbox inheritance](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html)). Our helper is launched by the AI tool, not by the app, so that recipe does not apply as written; what happens when such a tool is launched by a different, unsandboxed parent is **[not verified]** on an Apple page.
- An in-app HTTP server would need the `com.apple.security.network.server` entitlement (same archive page).

Sources: [SDK list](https://modelcontextprotocol.io/docs/sdk), [swift-sdk](https://github.com/modelcontextprotocol/swift-sdk) and its [releases](https://github.com/modelcontextprotocol/swift-sdk/releases), [typescript-sdk](https://github.com/modelcontextprotocol/typescript-sdk) and its [releases](https://github.com/modelcontextprotocol/typescript-sdk/releases), [TypeScript SDK, protocol versions](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/protocol-versions.md). Counts come from the GitHub API on the day.

**What the tiers mean.** Tier 1 requires a 100% conformance pass rate, new protocol features before each specification release, issue triage within two business days and a stable release. Tier 3 is "experimental, partially implemented, or specialized", with no minimum on any of those ([SDK tiers](https://modelcontextprotocol.io/community/sdk-tiers)).

**The Swift SDK and the current protocol.** The repository has one open tracking issue per change of the 2026-07-28 revision, all opened on 2026-06-06 and all still open, including the one that matters most, "Make MCP Stateless" ([#245](https://github.com/modelcontextprotocol/swift-sdk/issues/245)). A community pull request adding both protocol generations is open and under active review, not merged ([#314](https://github.com/modelcontextprotocol/swift-sdk/pull/314)). The SDK was close to unmaintained in late 2025; new maintainers were announced in January 2026 with a draft roadmap whose first item is reaching tier 2 ([#173](https://github.com/modelcontextprotocol/swift-sdk/issues/173)). It is still listed as tier 3.

**Does an old-protocol server still work?** The specification's compatibility matrix says a client that supports both generations works with an old-protocol server by falling back to `initialize`, while a client that supports only the new generation fails ([Versioning, backward compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning#backward-compatibility-with-initialization-based-versions)). Claude Code documents the first behaviour: it asks stdio and HTTP servers whether they support the newer revision and connects on the earlier handshake to those that do not ([Claude Code, MCP client runtimes](https://code.claude.com/docs/en/mcp#mcp-client-runtimes)). So a server built on Swift SDK 0.12.1 is documented to work with Claude Code today. For Claude Desktop's chat and for other vendors' tools this is **[not verified]**, and it holds only as long as clients keep the fallback.

**A warning about tracking `main`.** An issue opened on 2026-11-08 reports that, since a change merged on 2026-10-31 (on `main`, not in 0.12.1), the SDK's stdio transport crashes when started by a Node.js-based client, which according to the report includes Claude Desktop and Claude Code ([#327](https://github.com/modelcontextprotocol/swift-sdk/issues/327)). I did not reproduce it. Consequence: pin the exact release, do not depend on the branch.

**Reading.** The TypeScript SDK is clearly the more mature one. But choosing it puts the server in a different language from the rules, which is the larger cost for this project (section 4). The SDK risk is acceptable only because what we need from it is small: one stdio transport, a list of tools, a call handler. If it fails, the wire format is simple enough (one JSON-RPC message per line) that replacing the adapter does not touch the core.

Whether Swift SDK 0.12.1 builds with the Command Line Tools alone (its manifest requires Swift tools 6.1 and depends on `swift-nio`, `swift-log`, `swift-system` and an event-source package) is **[not verified]**.

## 4. One set of rules for the app and the server

### 4.1 The options

| Option | Rules written once? | Notes |
|---|---|---|
| **Shared Swift library used by both** (recommended) | ✅ | The app target and the bridge target link the same library. Both open the same file. Needs SQLite's multi-process guarantees (4.2) and a way for the app to notice outside changes (4.3). |
| **The server calls into the running app** (the helper forwards each call over a Unix socket or XPC, or the server is inside the app) | ✅ | One writer, instant interface updates. But it works only while the app runs, or needs a second path for when it does not, which brings back the first option anyway. |
| **Constraints in the schema only**, each process with its own code | ⚠️ partly | Catches bad data whoever writes, but cannot express whole operations, and error messages are terse. A safety net, not a home for the rules. |
| **Rules reimplemented in TypeScript** | ❌ | Two implementations to keep equal by hand. The earlier data-format note already flagged schema validation in Swift and TypeScript drifting apart. |
| **TypeScript server wrapping a Swift command-line tool** (runner-up) | ✅ | The command is the shared library with a text interface; the server holds no rules. |

Two layers are worth having together: **operations** in the library (for example "split a task into steps" replaces one estimate with several steps in a single transaction and rejects a split whose steps have no outcome), and **constraints** in the schema for what must never be false (an estimate is a positive whole number, a step belongs to an existing task).

### 4.2 What SQLite guarantees for two processes on one file

- Several processes may have the same database open and read at the same time, but "only one process can be making changes to the database at any moment in time" ([SQLite FAQ, question 5](https://sqlite.org/faq.html#q5)).
- In WAL mode "readers do not block writers and a writer does not block readers", and "there can only be one writer at a time". All processes must be on the same computer; WAL does not work over a network file system. WAL mode is persistent: once set, the file stays in WAL mode for whoever opens it next ([Write-Ahead Logging](https://sqlite.org/wal.html)).
- A writer that finds the database locked gets `SQLITE_BUSY`. A busy timeout makes it wait and retry for up to the given time instead ([`sqlite3_busy_timeout`](https://sqlite.org/c3ref/busy_timeout.html), [`PRAGMA busy_timeout`](https://sqlite.org/pragma.html#pragma_busy_timeout)). Even in WAL mode there are rare cases where a read returns `SQLITE_BUSY`, for example while the last connection is closing or while recovery runs after a crash, "so applications should be prepared" ([WAL, section 9](https://sqlite.org/wal.html#sometimes_queries_return_sqlite_busy_in_wal_mode)).
- In WAL mode a reader sees a fixed snapshot. A transaction that starts by reading and later tries to write fails with `SQLITE_BUSY_SNAPSHOT` if another connection wrote in between; starting the transaction with `BEGIN IMMEDIATE` avoids this ([Isolation in SQLite](https://sqlite.org/isolation.html), [Transactions](https://sqlite.org/lang_transaction.html)).
- Foreign key enforcement is off by default and "must be enabled separately for each database connection" ([Foreign keys](https://sqlite.org/foreignkeys.html)). A process that forgets it silently skips those checks: one more reason for both processes to open the database through the same library function.
- `STRICT` tables reject values of the wrong type instead of storing them ([STRICT tables](https://sqlite.org/stricttables.html)); `CHECK` constraints and triggers with `RAISE` cover simple rules ([CREATE TRIGGER](https://sqlite.org/lang_createtrigger.html)).

**What GRDB adds** (v7.12.0, 2026-11-01). Its guide on sharing a database between processes recommends `DatabasePool`, which opens the file in WAL mode; a busy timeout (`busyMode = .timeout(…)`) in every process that writes; and notes that GRDB opens all write transactions as `IMMEDIATE`, which prevents the snapshot failure above. It also recommends protecting the first opening with `NSFileCoordinator`, because two processes may try to create or migrate the database at once, and having the process that did not migrate check that the schema version is the one it expects ([GRDB, Sharing a Database](https://github.com/groue/GRDB.swift/blob/master/GRDB/Documentation.docc/DatabaseSharing.md)).

The same guide opens with a caution that deserves quoting: "Always consider sharing plain files, or any other inter-process communication technique, before sharing an SQLite database", because errors from sharing are hard to prevent and to test. Its hardest cases are specific to iOS (an app killed for holding a lock while suspended). For two short-transaction processes on a Mac the guarantees above are the relevant ones, but the caution is a reason to keep transactions short and to test the two-process case deliberately.

### 4.3 The app does not see what the bridge writes

GRDB's database observation "does not detect changes performed by external processes"; the guide suggests a cross-process notification (for example a Darwin notification, a system-wide signal with no payload) posted by the writer, after which the receiver reloads ([same guide](https://github.com/groue/GRDB.swift/blob/master/GRDB/Documentation.docc/DatabaseSharing.md)). The cheap alternative is reloading when the app's window becomes active. Either way, the app must not assume it is the only writer.

## 5. Alternatives to MCP

| | What it is | Strengths | Limits |
|---|---|---|---|
| **MCP server** | Tools with typed input that the AI tool lists and calls | Works in AI tools that cannot run commands; input schema validated; errors go back to the model so it can correct itself ([MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)) | Tool definitions cost tokens (section 6); an SDK to depend on |
| **Command-line tool** | The core as a command, for example `daycoach summary` or `daycoach task split 12 --steps …`, printing compact text or JSON | No protocol and no SDK; testable by hand; Claude Code's own cost guidance calls command-line tools "more context-efficient than MCP servers because they don't add any per-tool listing" ([Claude Code, costs](https://code.claude.com/docs/en/costs#reduce-mcp-server-overhead)) | Only for AI tools that can run shell commands; the model must be told the command exists and how to use it; shell quoting of free text such as notes |
| **Agent skill** | A folder with a `SKILL.md` of instructions, plus optional scripts, that the AI loads when relevant | About 100 tokens until used; can bundle a script or name a command to run, and pre-approve it ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview), [Claude Code, skills](https://code.claude.com/docs/en/skills)) | Not a channel to the data by itself: instructions are "a request, not a guarantee" ([Claude Code, features overview](https://code.claude.com/docs/en/features-overview)). It needs the command-line tool or the MCP server underneath |
| **App Intents** | Actions a Swift app declares to the system | Give Siri, Spotlight and Shortcuts access to the same operations ([App Intents](https://developer.apple.com/documentation/appintents)); a terminal agent could run a shortcut with the `shortcuts run` command (macOS manual page `shortcuts(1)`) | Apple's documentation and its June 2026 developer announcement describe App Intents as connecting apps to Siri and Apple Intelligence; I found no Apple documentation of third-party AI tools calling an app's intents ([Apple newsroom, 2026-06](https://www.apple.com/newsroom/2026/06/apple-aids-app-development-with-new-intelligence-frameworks-and-advanced-tools/)). Awkward for structured input and output |
| **Custom URL scheme** | `daycoach://…` links handled by the app | Good for navigation ("show this task") | One-way: no result comes back to the caller; Apple warns to "limit the available actions to those that don't risk the user's data" ([Defining a custom URL scheme](https://developer.apple.com/documentation/xcode/defining-a-custom-url-scheme-for-your-app)). Not suitable for reading or changing data |

**Reading.** The alternatives are not exclusive, and the recommended structure makes two of them nearly free: once the core is a library, a command-line face and an MCP face are both thin. A skill is then the place for *how to use* either one. Which form the AI's coaching behaviour should take (skills, MCP prompts or resources, instructions) is the subject of issue #3 and is not covered here. App Intents are worth remembering for iteration 3 (Shortcuts, Focus), not as the AI bridge.

## 6. Reducing the tokens spent

**Where tokens go.** Three places: the tool definitions sent with every request, the results of each call, and the number of calls.

**Definitions.**

- Anthropic's API documentation gives the order of magnitude: a typical setup with five servers "can consume ~55k tokens in definitions before Claude does any work", and tool search (loading definitions only when needed) "typically reduces this by over 85 percent" ([Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). The same page says standard tool calling is the better fit below about ten tools. Any use of tools also adds a fixed tool-use system prompt per request ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing)).
- Claude Code defers MCP tool definitions by default: "only tool names and server instructions load at session start". It cuts server instructions and upfront tool descriptions at 4,096 characters, and advises putting the important words first ([Claude Code, tool search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search)). Whether Claude Desktop's chat defers definitions the same way is **[not verified]**.
- The specification now says servers should return tools in a deterministic order "to enable client-side caching and improve LLM prompt cache hit rates" ([Key changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- Practical consequence: **few tools, each a whole operation**. Anthropic's guidance for tool authors recommends tools that "consolidate functionality, handling potentially multiple discrete operations … under the hood" rather than one tool per database action ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents), September 2025). For this app that points to something like six to eight tools (read the summary, list ready tasks, add or edit a task, split a task into steps, change an estimate, set the day plan), not a tool per table.

**Results.**

- The summary is the main lever, and it is the app's job by design ("the app does the mechanical work"). One call returning a digest of history, notes and ready tasks replaces many small reads.
- Return only what informs the next action. The same Anthropic article reports that resolving long opaque identifiers into short or meaningful ones improves precision, and suggests a `response_format` parameter with "concise" and "detailed" values; in its example the concise form uses about a third of the tokens. It also recommends pagination, filtering and truncation with sensible defaults, and error messages that say how to fix the input.
- Compact text costs less than indented JSON; the earlier data-format note measured this on a test dataset (section 3.2 of [that note](2026-11-01-data-format.md)).
- Claude Code warns when an MCP result exceeds 10,000 tokens and by default limits it to 25,000 ([Claude Code, MCP output limits](https://code.claude.com/docs/en/mcp#mcp-output-limits-and-warnings)). A summary should stay far below the first figure.

**Resources versus tools.** In the specification, tools are "model-controlled" (the model decides to call them), resources are "application-driven" (the host application decides how to include them) and prompts are "user-controlled" ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [prompts](https://modelcontextprotocol.io/specification/2026-07-28/server/prompts)). In Claude Code a resource enters the conversation when the user references it with `@`, and Claude Code also gives the model tools to list and read resources ([Claude Code, MCP resources](https://code.claude.com/docs/en/mcp#use-mcp-resources)). So a resource is not cheaper in itself: it costs its content when read, like a tool result. Exposing the summary as a **tool** is the form that works the same in every client; a resource can be added later for clients where the user attaches context by hand.

**Many tools at once.** Anthropic's article on running code against MCP servers reports a reduction "from 150,000 tokens to 2,000 tokens" when the model loads only the definitions it needs and filters results in code ([Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp), November 2025). That addresses setups with hundreds of tools; with fewer than ten it does not apply, but it is the same argument that makes a command-line tool cheap for a terminal agent.

## 7. Opening the AI tool on a specific folder

IDEA.md asks whether, when an AI session starts, the app can open the AI tool "on the right project". For this app that means a folder (for example one that holds the skills and the MCP configuration for the day coach).

**From the app's side.** A Mac app opens a URL, including a custom-scheme one, with `NSWorkspace.shared.open(_:)` ([NSWorkspace open](https://developer.apple.com/documentation/appkit/nsworkspace/open(_:))) and can open a file or folder with a chosen app through `open(_:withApplicationAt:configuration:completionHandler:)` ([documentation](https://developer.apple.com/documentation/appkit/nsworkspace/open(_:withapplicationat:configuration:completionhandler:))). Launch arguments can be passed through `OpenConfiguration.arguments`, but "if the calling process is sandboxed, the system ignores the value of this property" ([arguments](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration/arguments)).

**What the AI tools document.**

| Tool | Documented way | Limits |
|---|---|---|
| Claude Code (terminal) | Deep link `claude-cli://open?cwd=<absolute path>&q=<url-encoded prompt>`: opens a new terminal window with Claude Code in that folder and the prompt filled in. From the shell: `open "claude-cli://open?cwd=…"` ([Launch sessions from links](https://code.claude.com/docs/en/deep-links)) | The prompt is filled in but "not sent until you press Enter"; maximum 5,000 characters. The link handler is registered only after the user has sent something in an interactive session on that Mac. It uses the terminal app of the most recent session |
| Claude Code in VS Code | `vscode://anthropic.claude-code/open?prompt=…` opens a Claude Code tab ([VS Code, launch from other tools](https://code.claude.com/docs/en/vs-code#launch-a-vs-code-tab-from-other-tools)) | Opens in "whichever window is currently focused"; no parameter for a folder |
| Claude Desktop | `claude://code/new` opens the new-session page; the documented parameters name an SSH connection, a folder on the remote machine and a prompt ([Desktop, open an SSH session from a link](https://code.claude.com/docs/en/desktop#open-an-ssh-session-from-a-link)) | A parameter for a **local** folder is not documented: **[not verified]**. I found no documented link that opens a Desktop chat on a given project |
| Codex CLI | `--cd` / `-C <dir>` sets the working directory ([Codex CLI reference](https://developers.openai.com/codex/cli/reference)) | A command-line flag, so the app would have to open a terminal and run the command; no deep link found in that page |

**Reading.** It is feasible today for Claude Code with one line of Swift (open a `claude-cli://` URL with the folder and a starting prompt such as "Read the summary and propose which key tasks to break into steps"), with two conditions the app cannot control: the handler must already be registered, and the user must press Enter. That second condition is a reasonable safeguard, not a defect. For other tools the app would have to launch a terminal command, which is more fragile and impossible from a sandboxed app as documented above. A sensible design is a user setting holding the URL or command template to open, with the Claude Code link as the documented default.

## 8. What iteration 1 should already do

None of this requires AI work in iteration 1; each item is a choice that costs little now and avoids a rewrite later.

1. **One Swift package, with the core as its own library target.** The library holds the records, the migrations, the operations and the summary; it does not import SwiftUI or AppKit. The app is a second target that depends on it. The bridge will be a third target.
2. **Every change goes through a named operation in the core.** The interface never runs SQL. Each operation (add a task, change an estimate, split a task into steps, record a pomodoro with its note, set the day plan) validates its input, runs in one transaction and returns either the result or a typed error with a message a person can act on. These operations become the AI's tools almost one to one, and their error messages become the tool errors.
3. **Rules that must never be false also go in the schema**: `STRICT` tables, `NOT NULL`, `CHECK` (for example estimate greater than zero), foreign keys. Foreign key enforcement must be on for every connection, which is one more thing the single opening function guarantees.
4. **Open the database as if it were already shared**: `DatabasePool` (WAL mode), a busy timeout, short transactions, never a transaction held open while waiting for the user. One function in the core decides where the file is and how it is opened.
5. **Migrations belong to the core, and a process checks the schema version before use**, so that an older bridge refuses to touch a newer database instead of corrupting assumptions.
6. **The summary is a pure function in the core** that takes the database and returns compact text, with a test that keeps its size in check on a realistic amount of history. The roadmap already asks for a schema that makes this summary easy.
7. **Short, stable identifiers.** Whole-number row identifiers for tasks and steps rather than long random ones: they cost fewer tokens and, according to Anthropic's guidance cited above, models handle them more reliably.
8. **The interface must not assume it is the only writer**: reload from the database when the window becomes active, and keep in-memory state disposable. Adding a cross-process notification later is then a small change.
9. **Do not adopt the sandbox without a reason.** If it becomes necessary, the database location (item 4) is the only thing that moves, to an app group container.

## 9. Open questions

- **Does the Swift SDK connect to the tools actually used?** Try a ten-line stdio server on the pinned release with Claude Code and with Claude Desktop before writing any tool. This is the first task of iteration 2 and decides between the recommendation and the runner-up.
- **Which AI tool comes first?** A terminal coding agent can use a command-line tool and a skill; a desktop chat app needs MCP. The answer orders the work (and connects to issue #3).
- **Who confirms the AI's changes?** MCP clients ask the user to approve tool calls, with rules that differ per client. Whether the app should also keep a record of what the AI changed (to review or undo it) is a product decision, not researched here.
- **How does the app notice the bridge's writes?** Reload on activation, a Darwin notification, or both: to be chosen by trying it.
- **Does the bridge need the app?** The recommendation says no. If a tool should also act on the running app (for example "start a pomodoro on this step" starting the timer), that one operation needs a channel to the app, and the question of section 4.1 reopens for it alone.
- **Where is "the right folder" for an AI session?** A dedicated folder with the skills and the MCP configuration, or the folder of the work the task is about. Depends on issue #3.

### Not verified, in one place

- Claude Desktop's chat falling back to the old handshake with a 2025-11-25 server; Claude Desktop accepting a plain local HTTP server; Claude Desktop deferring tool definitions.
- A `claude://` parameter that opens a local folder.
- The behaviour of a sandboxed helper with the `inherit` entitlement when launched by a process other than its app.
- The stdio crash reported in swift-sdk issue #327 (read, not reproduced).
- Swift SDK 0.12.1 building with the Command Line Tools alone.
- GRDB's default for foreign key enforcement (the SQLite default is off; I did not open the GRDB page that states its own default).
- Apple pages were read through their JSON form; wording is quoted where exact, summarised elsewhere.
